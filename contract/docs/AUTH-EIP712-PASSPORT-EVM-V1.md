# AUTH-EIP712-PASSPORT-EVM-V1 — frozen byte contract of the `evm` arm

**Status**: frozen by PR-A phase A1 (2026/09/16); **extended by PR-B phase B1 (2026/09/16) with an
EIGHTH primary type, `OpenSwapShielded`**, in a way that changes no byte of the first seven — same
type strings, same type hashes, same vectors, same domain. A signature produced before B1 still
verifies. Any change to an existing byte would require a new version (`…-V2`) and a spec decision;
adding a type does not, because the type hash is what separates operations and a new one collides
with nothing.

The vector set is versioned separately and now spans two files: `…/FIXTURES-1`
(`passport-evm-v1.json`, the seven original types) and **`…/FIXTURES-2`
(`passport-evm-v1-swap.json`, the eighth)**. All hex in this document and in the fixtures is
lowercase and `0x`-prefixed; all integers in wallet JSON are base-10 strings.

**What this document is.** The `evm` arm of the account contract admits an ordinary Ethereum EOA
as a device. The wallet signs EIP-712 typed data; the circuit recomputes the same digest in-circuit
with `keccak256` and verifies the ECDSA signature with `secp256k1EcdsaVerify`. This file freezes
exactly what is signed, so that a wallet, a relayer, an auditor and the circuit can never disagree
about a byte. It is the `evm` arm's counterpart to the challenge preimages MIP-0013 §5.1 freezes
for the normative `jubjub` arm.

**Provenance.** The shape is AA-v3's `AUTH-EIP712-AA-V3-V1` (`acedward/AA-midnight-evm-experiment-v3`
@ `41de69d`), which the midnight-2-offers AA console signs today, with the Manager's `manager`,
`accountId` and `validUntil` replaced by the Passport account's own address and MIP-0013 freshness
(Q2 = A, Q8 = B in `plans/00034-passport-evm-account-zswap-questions.md`). The domain type string,
its type hash and the version hash are therefore identical to AA-v3's; the domain NAME and every
primary type are new.

**Toolchain.** Generated and checked under compactc 0.34.0 / language 0.26.0 / `--feature-zkir-v3`,
compact-runtime 0.19.0, `@noble/hashes` 2.2.0, `@noble/curves` 2.2.0, `ethers` 6.17.0.

## Domain

The exact domain type is

```
EIP712Domain(string name,string version,address verifyingContract,bytes32 salt)
```

with fields in that order. There is no `chainId`: a Midnight account has no EVM chain, and the
deployment is pinned by `salt` instead — the account's `evm_domain_salt`, a 32-byte network and
deployment domain fixed in the constructor (the MIP-0008 CAIP-2 style binding MIP-0013 §5.1
recommends). `verifyingContract` is the account's **alias**: the low 20 bytes of `keccak256` over
its 32-byte Midnight contract address. A Midnight contract has no EVM address and a wallet's
domain needs one; the alias is a deterministic, collision-resistant stand-in, and no one holds its
private key on Ethereum.

```
accountAlias    = keccak256(account)[12..32]                             (20 bytes)
domainSeparator = keccak256( domainTypeHash
                           || domainNameHash
                           || domainVersionHash
                           || addressWord(accountAlias)
                           || salt )                                     (160-byte preimage)
```

Frozen Keccak-256 hashes, with no reinterpretation or endian reversal:

| Value | Hash |
|---|---|
| Domain `encodeType` | `36c25de3e541d5d970f66e4210d728721220fff5c077cc6cd008b3a0c62adab7` |
| Domain name — `Midnight Passport Account` | `64d1c923e59da20d02c92dc0d6caa0868cb5c8ab17ee0658aafc5f0b72d56c85` |
| Domain version — `1` | `c89efdaa54c0f20c7adf612882df0950f5a951637e0307cdcb4c672f298b8bc6` |

A signature is therefore useless against another account contract (different alias) and against
another deployment of the same code (different salt).

## Primary types

One primary type per gated operation, so a signature authorising a withdrawal can never be read as
a device change: the separation is at the type-hash level, not the field level, and that is also
what lets a wallet show a distinct, meaningful action name. Every type has the same frame —

```
<Op>(bytes32 account,address owner,uint64 authNonce,<action fields>,bytes32 challenge)
```

— where `account` is the account contract's 32-byte Midnight address (the account id: Passport
accounts are one contract per user, so there is no separate id), `owner` the enrolled EOA,
`authNonce` the account's current MIP-0013 freshness counter, and `challenge` the arm's SHA-256
challenge core. Seven of the eight carry no `validUntil` (Q8 = B): freshness is `authNonce` alone,
and at most one signature per nonce can ever execute. The exception is `OpenSwapShielded`, and the
reason is structural rather than a matter of taste — an offer is the one authorisation that is
proved, published, and then executed by a STRANGER at a time the signer does not choose, so
"at most one executes" is true while "it executes when the maker still wants it to" is not. Its
`validUntil` is zero-means-none, so an offer that wants no deadline has none (Q33).

### Field notes

- **`recipient` / `recipientCoinPublicKey` / `recipientContract`** are one 32-byte word each. The
  three withdraw types are separate primary types rather than one type with a `recipientKind`
  discriminator (AA-v3's shape), because Passport already exports them as three circuits: the
  discriminator would be a second, redundant encoding of the choice the type hash has already made.
- **`entryHash` is `keccak256(entry)`**, over the 192-byte `InboxEntry` v1 container. The entry is
  ciphertext — nothing readable is lost by hashing it — and this keeps every field one word. The
  challenge binds the full 192 bytes, so a different entry behind the same hash is impossible
  without a keccak collision, and substituting a different entry changes the challenge and fails.
- **`challenge`** is the arm's SHA-256 challenge core (below). It is last in every type so a reader
  of the type string sees the readable action fields first.
- The action fields are signed **twice**: once as readable EIP-712 words, once inside `challenge`.
  Readability is for the human; the challenge is what additionally pins the witness values the
  wallet cannot see (AUTH-10, e.g. which coin a shielded withdrawal spends).
- **`OpenSwapShielded` (type 8)** is the largest type and the only one with a `uint8`. Its twelve
  fields are exactly the offer's terms, because an offer is read by a counterparty as well as by its
  maker: what leaves (`giveColor`, `giveAmount`), where it goes (`recipientKind` — `0` = open, the
  value released with no output at all; `1` = a named coin public key; `2` is refused by the circuit
  — and `recipient`, which MUST be all-zero when the kind is `0`), what must arrive (`wantNonce`,
  `wantColor`, `wantAmount`), and until when the authorisation is live (`validUntil`, `0` = none).
  **The two 192-byte inbox entries are deliberately NOT fields.** They are ciphertext, so a wallet
  gains nothing from a `keccak` word of them, and they would cost two more words of an already
  416-byte preimage; the `challenge` binds all 384 bytes of them, together with the witness coin, so
  they are pinned exactly as tightly as if they were here. Offers are the one place where the
  give/want legs are a price rather than a transfer, which is why `recipientKind` is a readable
  field rather than three separate types: the SAME signed terms have to describe both shapes for a
  taker to compare them.

## ABI word rules

Each field is one standard 32-byte ABI word.

| Type | Encoding |
|---|---|
| `bytes32` | the 32 bytes, unchanged |
| `address` | 12 zero bytes, then the 20 address bytes |
| `uint8` | 31 zero bytes, then the value (type 8's `recipientKind` only) |
| `uint64` | unsigned big-endian, left-padded to 32 bytes |
| `uint128` | unsigned big-endian, left-padded to 32 bytes |

The TypeScript API accepts integers only as `bigint`, and the `eth_signTypedData_v4` JSON
serializes them only as base-10 strings. Byte values serialize as lowercase `0x` hex.

## The challenge core

`challenge` is produced by the contract's exported pure circuits
`challenge_<op>_with_evm(...)` and is the MIP-0013 §5.1 preimage with the key encoded as the
device's 20-byte Ethereum address:

```
dst        = persistentHash([ pad(64, "midnight:account:auth:evm:v1:<op>") ])
challenge  = persistentHash([ dst, self_addr, address, ...args, ...witness_values, auth_nonce ])
```

`persistentHash` IS SHA-256 over the compiler's field-aligned binary encoding, so this layer is
**not** reproducible with an EVM toolchain alone: an independent signer obtains it either from the
contract's exported pure circuit (the client's route) or from the Rust signer's transcription (the
`crossimpl` route), exactly as the other two arms do. Everything above the challenge — the entire
EIP-712 layer this document freezes — is pure keccak and is reproducible with ethers alone.

The DST family and the derivations frozen alongside it, all arm-marked so no preimage of one arm
can be read as another's (SIG-1):

| Family | String |
|---|---|
| Device entry | `midnight:account:device:evm:v1` |
| Boot commitment | `midnight:account:boot:evm:v1` |
| Per-operation challenge | `midnight:account:auth:evm:v1:<op>`, `<op>` ∈ `withdraw_unshielded`, `withdraw_shielded`, `withdraw_shielded_to_contract`, `append_inbox`, `rotate_enc_key`, `add_device`, `remove_device`, `open_swap_shielded` |

The device entry binds the account address, the 20-byte Ethereum address, the epoch and the use
counter; the boot commitment binds the salt and the address. The `evm` arm has no envelope id (the
k256 arm's v2 derivations carry one): an EIP-712 digest is already a complete, unambiguous envelope.

## Signature transport

The only wire form is 65 bytes `r || s || v`.

- `r` and `s` are unsigned 32-byte big-endian scalars in `[1, n-1]`.
- `v` is `0`, `1`, `27` or `28` and normalises to recovery bit 0 or 1. **Nothing in the contract
  sees `v`**: the circuits take the public point as an explicit argument, and `v` exists only so a
  client can recover that point from one signature at enrolment.
- The **client** normalises to low-S (`s <= n/2`) so a call has one canonical wire form, and every
  frozen vector is low-S. The **contract accepts both S forms**, as Passport's other ECDSA arm
  does. ECDSA is malleable — `(r, s)` and `(r, n-s)` verify the same digest under the same key —
  and the rolling single-use device entry, not a canonicality rule, is what makes the twin
  non-replayable (SIG-4): whichever of the two lands first consumes the entry and advances
  `auth_nonce`, and the other then aborts on the consumed entry.
- Measured, and worth knowing: **ethers refuses to parse a high-S signature at all**
  (`non-canonical s`), so a twin cannot arrive through ordinary Ethereum tooling; it has to be
  crafted deliberately, and crafting it buys nothing. Every fixture carries its twin so the
  property is testable in both directions.

## Point transport

The recovered Compact argument is `Secp256k1Point { x, y, identity: false }`, both coordinates
unsigned 32-byte big-endian values.

```
address = keccak256(x || y)[12..32]        // secp256k1EthereumAddress(pk) in Compact
```

The seam re-derives the address from the presented point and compares it with the enrolled one, and
rejects the point at infinity by coordinates (Passport S12). A point that is not the device's key
therefore fails before the signature is examined. Note that compact-runtime 0.19.0 additionally
refuses the flagged identity point inside `secp256k1PointX/Y` itself (questions file Q22).

## The fixture set
