# The `ed25519` arm: a Solana wallet as an account device

Project 00047 (2026/09/30). A Passport account can be controlled by a Solana wallet
(Phantom, or any wallet with Ed25519 `signMessage`): the account's device is the wallet's
public key, and every gated call carries a signature the circuit verifies with the
standard library's `ed25519Verify<#n>` (compactc 0.35.0). The wallet needs no SOL and sends
no Solana transaction; it only signs messages.

## What the wallet signs (message format F3 v2)

On this arm the message **is** the approval screen. Each gated circuit renders, from the
arguments it executes on, a fixed-length message of printable ASCII, and the wallet signs
exactly those bytes. A swap offer reads:

```
Night Market - stagenet
Swap offer
Give base units 10000000
Give token e934b965a454ed6857080e9956ea83fb5542e0a860e96ce91daf35f5d7b02c9f
This site labels it: 10.000000 twUSDC
Get base units 20000
Get token ad2ba014014e6ec705357be9db5d3ad6f535d4bef6576f84a461f23b313a2e8e
This site labels it: 0.00020000 twBTC
Taker anyone
Expires 2026-10-01 13:34:56 UTC
Account 7775594c1df2808a nonce 17
Digest 82d206a409bcc4b372398a227667673b0918ba4a5cf3a84a852c76b31993d512
```

and a shielded withdrawal:

```
Night Market - stagenet
Withdraw shielded
Base units 10000000
Token e934b965a454ed6857080e9956ea83fb5542e0a860e96ce91daf35f5d7b02c9f
This site labels it: 10.000000 twUSDC
To key dbf68449cff10c89
Account 823656ad6d70be82 nonce 0
Digest cbf0177b2b60e5996058cb5a4a498041cfa14d8c48085811994bb6af222d7a6c
```

| Line | Where it comes from |
|---|---|
| label (24 bytes) | chosen by the dApp, e.g. its name and network; printable ASCII, checked in-circuit |
| operation | fixed per circuit (`Swap offer`, `Withdraw shielded`, `Withdraw unshielded`, `Withdraw to contract`, `File inbox note`, `Rotate encryption key`, or `Cancel all open offers`, see below) |
| `Base units` | **enforced**: the exact base-unit amount the call moves, in decimal |
| `Token` | **enforced**: the token's full 32-byte id (its colour, which is the registry's `tokenId`), in hex |
| `This site labels it:` | **the site's claim, marked as such**: the same amount with the site's decimal point, and the site's symbol for the token. Its digits are checked against the amount, so the site chooses only where the point goes (0..18 decimals) and the symbol (1..8 printable characters, no space). An unknown token, or one the arm cannot render, is labelled in base units under `?` |
| recipient, taker, key, entry | the first 8 bytes of the value in hex, computed in-circuit |
| `Expires` | the offer's `valid_until` (Unix seconds) as a UTC date and time, or `never` for 0 |
| account, nonce | the account address fingerprint and the live `auth_nonce`, computed in-circuit |
| digest | the call's challenge in hex: it binds everything the text abbreviates or cannot show (full addresses, the witness coin, the inbox entries, the network salt) |

Variable-width fields (numbers, the site label) are left-aligned and space-padded and end
their line, so every operation's message keeps one fixed length: withdraw unshielded 359
bytes, withdraw shielded 353, withdraw to contract 361, inbox note 186, rotate/cancel 196,
offer 558.

**What the circuit guarantees.** A signature verifies only over the bytes the circuit renders
from the call it executes, so a relay cannot change an amount, a token, a recipient, a
deadline or the nonce after the user approved. The base units, the full token id, the
fingerprints, the deadline's date and the nonce are BOUND to the executed values: the dApp
supplies their decimal digits (Compact has no division) and the circuit checks them, so for
each value exactly one text is valid. **What it does not guarantee** (Q25 B′): a token's
NAME and DECIMALS. There is no token registry on chain, so the circuit cannot tell which
symbol or how many decimals belong to a token; a dishonest page can put any symbol or decimal
point on the "This site labels it:" line, and the message says whose claim that line is. The
label on the first line is the dApp's choice too. What moves is always the base units of the
full token id on the two lines above it. The label and symbols are printable and cannot start
a new line.

**Shielded withdrawals spend the token they name** (audit C2): both circuits assert
`coin.color == color` for the `held_coin` witness's coin, as the offer does, so a prover whose
witness returns a coin of another token is refused.

**Limits.** Amounts of 10^24 base units or more cannot be rendered, so the arm refuses them
(10^6 tokens at 18 decimals). Deadlines are rendered from 1970 to 9999-12-31 23:59:59 UTC;
later ones are refused. Site decimals are 0 to 18 and symbols 1 to 8 characters without a
space.

**What it can never be mistaken for.** The messages start with printable ASCII and are at most
558 bytes, so they cannot parse as a Solana transaction (legacy, v0 or signed), they do not
start with the off-chain prefix `0xff "solana offchain"`, and they contain no Sign-In With
Solana statement. `assertSafeEd25519Message` checks all three before any wallet is asked.

The TypeScript renderer (`src/wallet/ed25519-message.ts`) is an independent implementation of
the same layout; `src/tests/ed25519-message-offline.ts` holds it byte-for-byte to the
contract's exported `ed25519_message_*` pure circuits over a 61-call golden corpus
(`src/tests/fixtures/ed25519-messages-v2.json`), and checks that the circuit refuses every
display input that does not describe the call.

### One device per account, and the cancel

The arm has **no device management** (Q27): no `add_device_with_ed25519` or
`remove_device_with_ed25519`, so an account's only device is the key it was activated with,
and no single phishing signature can enrol another key. `rotate_enc_key_with_ed25519` stays
because the market uses it as its on-chain **cancel** (Q30): re-affirming the account's
current encryption key lands a gated call, so `auth_nonce` moves and every outstanding approval
of the account (open offers included) stops verifying. The circuit renders the two cases
differently, from the account's live `enc_key`:

```
Night Market - stagenet            Night Market - stagenet
Cancel all open offers             Rotate encryption key
Your key does not change           New key 1a2b3c4d5e6f7a8b
Account … nonce 17                 Account … nonce 17
Digest …                           Digest …
```

so a page cannot pass a real key change off as a cancel, or the reverse.

## The circuits

Rows from compactc 0.35.0's `zkir-v3 mock-compile` (k=18 holds 262,135 usable rows; the bar is
235,000, a 10% headroom):

| Circuit | k | rows (F3 v2) | rows (F3 v1) | message bytes |
|---|---|---|---|---|
| `open_swap_shielded_with_ed25519` | 18 | 198,811 | 179,387 | 558 |
| `withdraw_shielded_to_contract_with_ed25519` | 18 | 167,433 | 155,864 | 361 |
| `withdraw_shielded_with_ed25519` | 18 | 161,685 | 150,104 | 353 |
| `withdraw_unshielded_with_ed25519` | 18 | 142,368 | 130,793 | 359 |
| `append_inbox_with_ed25519` | 18 | 128,489 | 128,569 | 186 |
| `rotate_enc_key_with_ed25519` | 17 | 128,164 | 128,174 | 196 |
| `activate_initial_device_with_ed25519` | 14 | 12,390 | 12,390 | none (permissionless) |

`add_device_with_ed25519` and `remove_device_with_ed25519` (v1: 128,139 and 130,097 rows) are
gone. For comparison, `open_swap_shielded_with_evm` is 245,050 rows at k=18 on the same
compiler.

**Keys and entries.** The device is a `Curve25519Point`. Entries and boot commitments use the
arm marker `ed` (`midnight:account:device:ed:v1`, `midnight:account:boot:ed:v1`); challenges
use `midnight:account:auth:ed:v1:<operation>` and bind, like the `k256` arm's, the account,
the key, every argument, every witness value (AUTH-10) and `auth_nonce`, plus the account's
sealed `evm_domain_salt` as its network salt.

**Safety.** Beyond `ed25519Verify`'s own checks (s < L by type; A and R canonical and in the
prime-order subgroup by type; A not the identity), the seam refuses R = identity, the one
case libsodium refuses that the standard library accepts. The client decodes strictly, passes
s unreduced, and verifies every signature with tweetnacl before any proof.

## Using it (client API)

Everything below is exported from both entry points (`src/index.ts` and the browser-safe
`src/browser.ts`).

### A device

```ts
import { Ed25519Device } from '.../contract/src/browser.js';

// Phantom (a software account; Ledger-backed accounts are refused by the pre-check):
const phantom = window.phantom.solana;
await phantom.connect();
const device = new Ed25519Device({
  publicKey: phantom.publicKey.toBytes(),          // or the base58 address
  sign: async (message) => (await phantom.signMessage(message, 'utf8')).signature,
  label: 'Night Market - stagenet',                // <= 24 printable ASCII characters
  tokens: (colourHex) => registry.get(colourHex),  // the site's label: { symbol, decimals } | undefined
});

// A test key (tweetnacl; the same scheme as Phantom):
const testDevice = Ed25519Device.fromSeed(seed32, { label, tokens });

// A key known only by its public half (a relay deploying for a user):
const forDeploy = new Ed25519Device({ publicKey: userPublicKey });
```

`device.address` is the Solana address, `device.pk` the circuit's point, and
`device.entryAt(account, epoch, counter)` / `device.bootCommitment(salt)` the arm's
derivations. `tokens` only feeds the "This site labels it:" lines: a display the arm cannot
render (`isRenderableTokenDisplay`: a symbol of 1..8 printable characters without a space,
decimals 0..18) is labelled `?` in base units, and the base units and full token id are shown
whatever it returns.

### Deploy and activate (the relay pays)

```ts
import { CustodyAccount, contractForEd25519Account, ed25519AccountWaves } from '...';

const withSwap = true;                               // a market account carries the offer circuit
const compiled = contractForEd25519Account({ withSwap });
const account = await CustodyAccount.deploy(providers, compiled, forDeploy, encKeys, {
  waveTwoCircuits: ed25519AccountWaves({ withSwap }).waveTwo,
  // retireAuthority defaults to true: no key stays above the device seam
});
```

Wave 1 carries the deposits, the activation and the arm's five gated circuits
(`ED25519_GATED_BASES`: the two shielded withdrawals, the unshielded withdrawal, the inbox
append and `rotate_enc_key`; `ED25519_GATED_IN_WAVE_ONE` = 5, eight operations in all); wave 2,
the maintenance update that retires the authority, carries the offer circuit for a market
account and nothing else (without it, wave 2 only retires the authority).
`armCircuits('ed25519')`, `contractForArms(['ed25519'])`, `ed25519AccountWaves` and
`ed25519AccountCircuits` list no device circuit.
Activation needs no signature: the boot commitment binds the key. A relay that wants proof of
key possession first (for example before a once-per-key faucet claim) asks the wallet to sign
`ed25519PossessionMessage({ label, publicKeyBase58, purpose, nonce })`, which authorises
nothing on chain.

### Gated calls

`CustodyAccount` is arm-generic: `withdrawShielded`, `withdrawUnshielded`, `appendInbox` and
`rotateEncKey` take the `Ed25519Device` like any other device; `addDevice` and `removeDevice`
are refused with a reason (one device per account). `rotateEncKey` needs the account's current
key in the call context (`ctx.encKey`, which `CustodyAccount.callContext` reads from the
ledger): with the same key it is the cancel. Under the hood,
`authorise(device, ctx, request, useCounter)` calls `device.sign`, which:

1. refuses a shielded withdrawal whose coin is of another token than it names (C2), then
   computes the challenge with the contract's own `challenge_<op>_with_ed25519`;
2. renders the message in TypeScript and compares it with the contract's
   `ed25519_message_<op>` output, refusing to continue on any difference;
3. refuses bytes that could be read as a Solana transaction, an off-chain message or a SIWS
   request;
4. asks the wallet through the sign callback;
5. verifies the signature with tweetnacl (another key, other bytes, or a Ledger-wrapped
   signature fail here, before any proof);
6. decodes R strictly (not the identity) and takes s unreduced (s >= L is refused).

The circuit's trailing arguments are `authArgs(auth)` = `(pk, use_counter, sig, show)`.
`device.preview(ctx, request)` returns the text without asking the wallet, for the dApp's own
confirmation panel.

### Offers

```ts
const ctx = await account.callContext();              // address, auth_nonce, network salt, enc key
const counter = await account.resolveUseCounter(device);
const auth = await device.signOffer(ctx, call, coin, counter);   // call: OfferCallArgs (offer.ts)
const offer = await buildOpenSwapOffer({
  ..., circuitId: 'open_swap_shielded_with_ed25519', call, authArgs: ed25519AuthArgs(auth),
});
```

`device.previewOffer(ctx, call, coin)` shows the text first. `call.validUntil` is Unix seconds
(the circuit compares it with the block time); sign a real one (C6), shown as `Expires <UTC>`.
`0` still means no deadline and reads `never`.

### Signing in the browser, proving on the relay

The relay must not trust bytes the browser sends. It rebuilds the authorisation from the call
itself, with the browser's 64-byte signature as the sign callback:

```ts
const onRelay = new Ed25519Device({ publicKey, label, tokens, sign: () => signatureFromBrowser });
const auth = await onRelay.sign(ctx, request, counter);   // or signOffer(ctx, call, coin, counter)
```

Every check above runs again on the relay (the challenge, the contract's own message, the
tweetnacl verification, strict R, s < L), so a signature over anything but this exact call
fails before the relay spends proving time.

## Toolchain and runtime

- **compactc 0.35.0** (`--feature-zkir-v3`), pinned by the release archive's SHA-256 and
  checked FAIL CLOSED (audit C9a): `scripts/compile-account.sh` runs
  `scripts/verify-compactc.sh` first on every toolchain (the host's `compact` CLI install of
  0.35.0, `docker/compactc-0.35.0.Dockerfile`, or a verified directory on PATH): the release
  archive must be there and match the pinned digest for the platform, and every binary a
  compile runs must equal the archive's copy. A toolchain it cannot check is refused (exit
  70), never skipped; `scripts/test-verify-compactc.sh` tests that.
- **compact-runtime 0.20.0 for the contract module only**: the generated module imports the npm
  alias `@midnight-ntwrk/compact-runtime-0.20` (`scripts/pin-contract-runtime.mjs`); compact-js
  2.5.5-rc.8 and midnight-js 5.0.0-beta.7 keep 0.19.0, and both share one
  onchain-runtime-v4 4.0.0-rc.3.
- **Two proof servers** until stagenet moves to dust/10: `midnightntwrk/proof-server:9.0.0-rc.8`
  for the contract circuits (ZKIR 3.1: rc.6 cannot read them) and `9.0.0-rc.6` for the
  wallet's DUST proof (stagenet requires dust/9).

### BREAKING for new deployments

- **Every circuit's verifier key changes** with the compiler. Accounts already deployed are
  unaffected (their keys are on chain); a client built from this branch cannot connect to an
  account deployed from an older build, and vice versa.
- **Rows grow on the secp256k1 arms** (same source, each compiler's own `zkir-v3`): every
  `evm` circuit +8,055, every `k256` circuit +2,864 (+8,615 for its two shielded spends); five
  `k256` circuits move from k=16 to k=17. The `jubjub` arm, the deposits, the activations
  and the bridge settles are unchanged.
- **The ERC20 bridge circuits cannot be driven** with the current SDK: runtime 0.20 binds a
  cross-contract call through a module provider on the circuit context, and compact-js
  2.5.5-rc.8 supplies none (`test:bridge-offline` fails with `ModuleResolutionError … the
  circuit context carries no module provider`). Accounts that bridge stay on PR #4's 0.34.0
  build until a compact-js with a `ContractModuleProvider` ships. The vault package itself
  stays on 0.34.0.
- **Runtime 0.20 validates curve points** at the type boundary: an off-curve `Secp256k1Point`
  is now a type error (one unit test adapted).
- **The security fix pass (P9.C, 2026/10/01) changes the `ed25519` arm again**, so its keys and
  messages differ from the first draft (`451f761`): the message format is F3 v2 (every
  `ed25519_message_*` circuit and every display input, `EdAmount`/`EdShow*`/`EdDeadline`,
  changed; the golden file is `ed25519-messages-v2.json`), the two shielded withdrawals assert
  the coin's colour, and `add_device_with_ed25519`/`remove_device_with_ed25519` are gone, so the
  account shape and its key-set fingerprint change. Accounts deployed from the first draft
  (stagenet test accounts only) keep their old keys and cannot be driven by this client. The
  client API changes are listed in the PR description.

### The safety matrix, on the real arm circuits

`src/tests/ed25519-safety.ts` runs each case at three layers: the client (strict decoding,
s < L, the tweetnacl pre-check), the strict compiled circuit called directly with typed
arguments, and the strict circuit's IR run by proof server rc.8's `/check` on a preimage the
lax twin (`scripts/ed25519-lax-twin.sh`, test-only: the two signature asserts removed) produces
for a malicious prover, with spike 3's typed substitutes where the bytes are not values of the
argument types. Results on `rotate_enc_key_with_ed25519` (k=17):

| Case | libsodium | client | compiled circuit (JS) | in-circuit (rc.8 `/check`) |
|---|---|---|---|---|
| valid (Phantom scheme) | accept | **accepted** | **accepted** | **accepted** |
| flipped message bit | reject | refused (tweetnacl pre-check: does not verify) | refused (`invalid signature`) | refused (`Failed direct assertion`) |
| flipped S bit | reject | refused (tweetnacl pre-check: does not verify) | refused (`invalid signature`) | refused (`Failed direct assertion`) |
| flipped R bit | reject | refused (the signature's R is not in the prime-order subg) | not callable (type) | no typed value |
| another key | reject | refused (tweetnacl pre-check: does not verify) | refused (`invalid signature`) | refused (`Failed direct assertion`) |
| wrong network (salt) | reject | refused (tweetnacl pre-check: does not verify) | refused (`invalid signature`) | refused (`Failed direct assertion`) |
| wrong account | reject | refused (tweetnacl pre-check: does not verify) | refused (`invalid signature`) | refused (`Failed direct assertion`) |
| replay (the nonce-0 approval at nonce 1) | reject | refused (tweetnacl pre-check: does not verify) | refused (`invalid signature`) | refused (`Failed direct assertion`) |
| S + L (malleated) | reject | refused (the signature's s is not below L (non-canonical;) | not callable (type) | no typed value |
| identity A (universal forgery) | reject | refused (the key is the identity) | refused (`device key is the identity`) | refused (`Failed direct assertion`) |
| small-order A (order 8) | reject | refused (the key has small order) | not callable (type) | refused (`Failed direct assertion`) |
| mixed-order A (A + T8) | reject | refused (the key is not in the prime-order subgroup) | not callable (type) | refused (`Failed direct assertion`) |
| non-canonical R (y = 1 + p) | reject | refused (the signature's R does not decode (strict RFC 80) | not callable (type) | refused (`Failed direct assertion`) |
| mixed-order R (rB + T8) | reject | refused (the signature's R is not in the prime-order subg) | not callable (type) | refused (`Failed direct assertion`) |
| R = identity, equation holds | reject | refused (the signature's R is the identity) | refused (`R is the identity`) | refused (`Failed direct assertion`) |

The same verdicts hold on `append_inbox_with_ed25519` (k=18). Real proofs: the valid preimages prove on rc.8; `/prove` refuses the negatives with 400.

`/prove`, fresh server, a warm-up and three timed runs: `rotate_enc_key_with_ed25519` (k=17,
